# WebKit `decodingInfo()` on Cocoa: source findings

All links are pinned to WebKit main at `c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6` (2026-11-11). "Inference" marks what the study did not read directly in the source.

**Path.** The web process validates the question, reads page settings, and calls the factory ([MediaCapabilities.cpp#L179-L209](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/Modules/mediacapabilities/MediaCapabilities.cpp#L179-L209)). With "GPU Process: Media" on (the Cocoa default, [UnifiedWebPreferences.yaml#L6743-L6753](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml#L6743-L6753), [PlatformEnableCocoa.h#L420-L422](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WTF/wtf/PlatformEnableCocoa.h#L420-L422)), that factory forwards to the GPU process ([WebProcess.cpp#L2700-L2703](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/WebProcess/WebProcess.cpp#L2700-L2703), [RemoteMediaEngineConfigurationFactory.cpp#L94-L102](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/WebProcess/GPU/media/RemoteMediaEngineConfigurationFactory.cpp#L94-L102)). There the Cocoa factory computes the answer synchronously ([RemoteMediaEngineConfigurationFactoryProxy.cpp#L53-L58](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/GPUProcess/media/RemoteMediaEngineConfigurationFactoryProxy.cpp#L53-L58), [PlatformMediaEngineConfigurationFactoryCocoa.cpp#L63-L194](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/PlatformMediaEngineConfigurationFactoryCocoa.cpp#L63-L194)).

## Recorded in Safari 26.6

Every Safari figure in this note was recorded in Safari 26.6 on macOS through `safaridriver` on 2026-11-11, on a display that reports HDR, so each declaration asks its HDR questions.

- Before the client searched for an HEVC level above the one its picture needs, one declaration asked 81 `decodingInfo` questions and took 250 to 290 ms. With that search, one declaration makes 89 asks, 84 of them distinct, and takes about 300 ms. The client builds a declaration before every playback start. A second declaration costs as much as the first, because WebKit keeps no answers.
- WebKit answers the questions one at a time, in its GPU process, in arrival order. Asking them all at once is no faster than asking them one after another. Each takes about 4 ms once warm. One question of a page's first declaration took 114 ms.
- Pending questions do not block the page. A synchronous `HTMLMediaElement.canPlayType` or `MediaSource.isTypeSupported` call for a type not asked before does block it. That call waits behind every pending question: about 265 ms behind 70 pending questions, and about 5 ms (at worst 10 ms) behind one.
- In the first declaration of a page, up to 71 questions were pending. The client's own `canPlayType` calls blocked the page for about 220 ms. The slowest single call took 204 ms.
- A declaration asked fresh from the browser and declarations served from the kept answers came out the same. This check, not the source, covers what VideoToolbox and AVFoundation read (see "Not established").

The other two browser engines were not recorded through `safaridriver`. [ADR 0049](https://github.com/streamarr/streamarr-adr/blob/main/adr/0049-capability-declarations-list-entries-and-an-output-fits-one-entry.adoc) states that their builds answered 300 HEVC questions in about 20 ms. Only WebKit has this cost.

## 1. HDR and the display

No WebKit code on the decodingInfo path reads the screen, HDR support, EDR headroom, gamut, or the window's display. The HDR fields only switch on codec-profile checks; everything else comes from VideoToolbox and AVFoundation.

- The three fields collapse into one flag; their values are not inspected ([Cocoa.cpp#L94](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/PlatformMediaEngineConfigurationFactoryCocoa.cpp#L94)):
  `bool hdrSupported = videoConfiguration.colorGamut || videoConfiguration.hdrMetadataType || videoConfiguration.transferFunction;`
- HEVC with HDR requires Main10, then asks VideoToolbox ([HEVCUtilitiesCocoa.mm#L64-L84](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm#L64-L84)). Dolby Vision with HDR requires profile 4, 5, 7 or 8; any supported Dolby Vision answer is `{ true, true, isHardwareAccelerated }` ([#L161-L206](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm#L161-L206)).
- AV1 ignores the fields (it checks size, frame rate and bitrate against the level); HDR comes from the codec string and only selects `MaxHDRPlaybackLevel` for `smooth` ([AV1UtilitiesCocoa.mm#L170-L178](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/AV1UtilitiesCocoa.mm#L170-L178)). VP9 checks that the fields agree with the codec string ([VP9UtilitiesCocoa.mm#L348-L362](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/VP9UtilitiesCocoa.mm#L348-L362)). H.264 refuses any HDR field ([Cocoa.cpp#L148-L155](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/PlatformMediaEngineConfigurationFactoryCocoa.cpp#L148-L155)).
- The GPU process receives screen HDR data only to set a MediaToolbox playback override ([GPUProcessMac.mm#L92-L110](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/GPUProcess/mac/GPUProcessMac.mm#L92-L110)). No WebKit code on the decodingInfo path reads it.
- The HEVC check reads the level in the codec string, and not the picture. Width, height, frame rate and bitrate are not passed in ([HEVCUtilitiesCocoa.mm#L113-L128](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm#L113-L128)):
  `if (parameters.generalLevelIDC > maxDecodeLevel) return std::nullopt;` and `info.smooth = parameters.generalLevelIDC <= maxPlaybackLevel;`
  Both limits come from VideoToolbox. H.264's level is not read: `smooth = true`, `powerEfficient = VTIsHardwareDecodeSupported(...)`.

## 2. Stability while the page stays open

Apart from audio with `spatialRendering: true`, the only run-time inputs found are page settings, plus power and screen size in one rare VP9 case. WebKit does not cache decodingInfo answers.

- Page settings, read on every call: allowed container and codec types, VP9 enabled, extensions enabled ([MediaCapabilities.cpp#L187-L195](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/Modules/mediacapabilities/MediaCapabilities.cpp#L187-L195)). They change only when the embedder updates preferences.
- `spatialRendering: true` only: macOS reads the output device's spatial preferences on every call ([SpatialAudioPlaybackHelperMac.cpp#L45-L66](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/audio/mac/SpatialAudioPlaybackHelperMac.cpp#L45-L66)); iOS reads whether the current route has spatial audio ([SpatialAudioPlaybackHelperIOS.mm#L103-L125](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/audio/ios/SpatialAudioPlaybackHelperIOS.mm#L103-L125)). The channel count compared is the configuration's, not the output's. Otherwise audio is only `MediaPlayer::supportsType` on the MIME string; channels, sample rate and bitrate are not read ([Cocoa.cpp#L160-L182](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/PlatformMediaEngineConfigurationFactoryCocoa.cpp#L160-L182)).
- VP9 with no hardware decoder on a battery device: AC power and attached screen size ([VP9UtilitiesCocoa.mm#L414-L446](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/VP9UtilitiesCocoa.mm#L414-L446)). `systemHasAC()` is cached at first read ([SystemBattery.mm#L89-L120](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/cocoa/SystemBattery.mm#L89-L120)). Inference from code search: only web processes get AC updates, and only web processes fill `PlatformScreen` on Cocoa ([PlatformScreen.cpp#L47-L51](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/PlatformScreen.cpp#L47-L51)), so in the GPU process both stay fixed.
- Not found: playback history or statistics, thermal state, low-power mode, display HDR, external display or GPU.
- No answer cache: each HEVC question calls `VTSelectAndCreateVideoDecoderInstance` and `VTCopyHEVCDecoderCapabilitiesDictionary` again ([HEVCUtilitiesCocoa.mm#L72-L84](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm#L72-L84)). Only the `supportsType` step is cached per MIME string for the GPU process's life ([MIMETypeCache.cpp#L70-L106](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/MIMETypeCache.cpp#L70-L106)).
- A refusal can be a cancelled reply. When the web process's connection to the GPU process closes, `connectionDidClose` ends in `invalidate()`, which cancels every pending reply ([Connection.cpp#L1316-L1355](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L1316-L1355), [#L1505-L1516](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L1505-L1516), [#L561-L577](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L561-L577), [#L1838-L1857](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L1838-L1857)). A reply that fails to decode is cancelled too ([Connection.h#L1150-L1164](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.h#L1150-L1164), [#L1241-L1251](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.h#L1241-L1251)). A cancelled reply calls the reply handler with value-initialized reply arguments ([Connection.h#L1254-L1265](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.h#L1254-L1265), [#L226-L228](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.h#L226-L228)). A value-initialized answer has `supported`, `smooth` and `powerEfficient` false ([PlatformMediaCapabilitiesInfo.h#L33-L35](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/mediacapabilities/PlatformMediaCapabilitiesInfo.h#L33-L35)). The decodingInfo reply handler passes it on ([RemoteMediaEngineConfigurationFactory.cpp#L99-L101](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/WebProcess/GPU/media/RemoteMediaEngineConfigurationFactory.cpp#L99-L101)), and `decodingInfo` resolves the promise with it ([MediaCapabilities.cpp#L261-L265](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/Modules/mediacapabilities/MediaCapabilities.cpp#L261-L265)). So the page cannot tell a cancelled reply from a refusal, and the client keeps no refusal. Inference: the connection closes when the GPU process ends.
- Asking refusals again costs little. Safari 26.6 on macOS refused 31 of the 84 questions of one declaration. A refusal took about 0.1 ms, and asking all 31 again took about 3 ms.

## 3. Threads and ordering

Each question runs on the GPU process's main run loop, one at a time, in arrival order. A `canPlayType` or `isTypeSupported` for a new type is synchronous IPC on the same connection, and the GPU process answers it after the decodingInfo messages that arrived first.

- The web process sends `sendWithAsyncReply(Messages::RemoteMediaEngineConfigurationFactoryProxy::CreateDecodingConfiguration(...))` ([RemoteMediaEngineConfigurationFactory.cpp#L94-L102](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/WebProcess/GPU/media/RemoteMediaEngineConfigurationFactory.cpp#L94-L102)) and resolves the promise in a queued event-loop task ([MediaCapabilities.cpp#L261-L265](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/Modules/mediacapabilities/MediaCapabilities.cpp#L261-L265)), so pending questions do not block the page.
- The GPU side opens the connection on the main run loop and dispatches these messages there ([GPUConnectionToWebProcess.cpp#L358-L368](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/GPUProcess/GPUConnectionToWebProcess.cpp#L358-L368), [#L1157-L1160](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/GPUProcess/GPUConnectionToWebProcess.cpp#L1157-L1160)).
- Each async message queues its own main-run-loop task ([Connection.cpp#L1567-L1577](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L1567-L1577)). A sync message gets its own task in the same queue ([#L208-L241](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/Platform/IPC/Connection.cpp#L208-L241)). `RunLoop` runs tasks first in, first out ([RunLoop.cpp#L128-L169](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WTF/wtf/RunLoop.cpp#L128-L169)).
- `canPlayType` and `isTypeSupported` reach `RemoteMediaPlayerMIMETypeCache::supportsTypeAndCodecs`, which blocks in `sendSync(...SupportsTypeAndCodecs...)` on a cache miss ([RemoteMediaPlayerMIMETypeCache.cpp#L84-L100](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebKit/WebProcess/GPU/media/RemoteMediaPlayerMIMETypeCache.cpp#L84-L100), [MediaSource.cpp#L1009-L1016](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/Modules/mediasource/MediaSource.cpp#L1009-L1016)). The cache is process-wide, so a repeated type returns at once.

## 4. HEVC levels

[hevc-level-capability.md](hevc-level-capability.md) records how WebKit reads the level of an HEVC question, on Cocoa and in its GStreamer port, and this section holds only what that note does not.

- The Cocoa factory asks `MediaPlayer::supportsType` about the whole content type before it parses the level and compares it with `MaxDecodeLevel` ([PlatformMediaEngineConfigurationFactoryCocoa.cpp#L83-L104](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/PlatformMediaEngineConfigurationFactoryCocoa.cpp#L83-L104), [HEVCUtilitiesCocoa.mm#L113-L120](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/cocoa/HEVCUtilitiesCocoa.mm#L113-L120)). The source cannot say which of the two refused a level. Inference: if `canPlayType` or `MediaSource.isTypeSupported` accepts the same string, the comparison with `MaxDecodeLevel` refused it.
- When the WebRTC provider reports a power-efficient decoder, `type: "webrtc"` turns an H.265 RTP type into an `hvc1` codec string and asks the same factory as `media-source` ([WebRTCProvider.cpp#L219-L265](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/mediastream/WebRTCProvider.cpp#L219-L265), [#L332-L372](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/mediastream/WebRTCProvider.cpp#L332-L372), [HEVCUtilities.h#L55](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/HEVCUtilities.h#L55), [HEVCUtilities.cpp#L233](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/HEVCUtilities.cpp#L233)).
- In the GStreamer port, an HEVC question at any level can still be refused by the decoding limits on size and frame rate ([GStreamerRegistryScanner.cpp#L1119-L1131](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/gstreamer/GStreamerRegistryScanner.cpp#L1119-L1131)), and by WPE's check of the HDR fields against the screen ([#L1133-L1148](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/gstreamer/GStreamerRegistryScanner.cpp#L1133-L1148)). Inference: GStreamer names profile 2 `main-10`, so the profile check passes.

## Not established

- What VideoToolbox reads behind its capability dictionary and `VTSelectAndCreateVideoDecoderInstance`: thermal state, power, external GPU, display. Inference: that call takes most of the time of a warm question, which is about 4 ms.
- What AVFoundation's `isPlayableExtendedMIMEType:` considers ([AVAssetMIMETypeCache.mm#L116-L122](https://github.com/WebKit/WebKit/blob/c46f252a2c4246a5a5cda58ce4ba7aed237bf1c6/Source/WebCore/platform/graphics/avfoundation/objc/AVAssetMIMETypeCache.mm#L116-L122)), and whether the MediaToolbox HDR override affects it. Its answers are cached per MIME string anyway.
- Whether the browser changes the relevant page settings at run time.
- Whether `DeferredMainRunLoopDispatcher` keeps dispatch order; the study did not read it.
- Code search ran against current main, not the pinned commit.
